# 目的
異なるフォーマットのCSV/Excelデータを、自社システムや特定のソフトに適合する形式へノーコードで変換する。

# 主要機能
- テンプレート管理: 変換元と変換先のペア設定を保存・再利用。

- 汎用インポート: CSV/Excel両対応（excelize活用）。

- マッピングUI: 左右の項目を紐付け。

- データ加工ロジック:

    - 固定値: 「1」などの定数。
    - 型変換: 日付、数値のフォーマット指定。
    - 単純結合: 複数列を1列に。
    - 変換実行: ドラッグ＆ドロップによる一括変換。

# 詳細要件
## ヘッダー抽出機能
- From解析: サンプルCSV/Excelを読み込み、1行目を項目名としてリスト化。

- To解析: 出力先（相手先指定のフォーマットなど）のサンプルを読み込み、出力すべき項目名をリスト化。

- 履歴保持: 一度読み込んだヘッダー構造はテンプレートとしてDBに保存し、次回はファイル選択不要にする。

## マッピング・変換ロジック
- マッピング: 画面上の項目を線で結ぶ。

- プレビュー: マッピングした結果、最初の数行がどう変換されるか画面上でリアルタイム確認できる機能（これがあると安心感が違います）。

- 出力形式: * CSV (カンマ/タブ区切り、囲み文字の有無)
    - Excel (シート名指定、特定のセル位置への書き込み)

## 変換の重ね掛け
TransformRule（JSON）の中身を、単なる設定値ではなく実行リストにしてしまいます。

```JSON
// transform_rule の中身（例）
[
  { "type": "join", "delimiter": "-" },
  { "type": "convert", "convert_type": "to_half" },
  { "type": "padding", "length": 10, "padChar": "0" },
  { "type": "prefix_append", "prefix": "ITEM_" }
]
```
この場合、DBの MappingType カラム自体が不要になるか、あるいは単に custom とだけ入れる形になります。

## ライセンス
個別のシリアルコードを送り、アプリ起動時に入力させます。

### PC情報の紐付け
#### 1. 準備：アプリ（exe）に組み込んでおくもの
Wailsでビルドする前に、プログラムに以下のロジックを実装しておきます。

- HWID取得機能: PC固有のIDを読み取るコード。
- 秘密の合言葉（ソルト）: あなただけが知る文字列（例: "MY-SECRET-2026"）。コード内に隠しておきます。
- 判定ロジック: 「HWID + 秘密の合言葉」をハッシュ化（計算）して、正解のキーを導き出す計算式。
- ライセンス画面: 初回起動時に「ID」を表示し、「キー」の入力を待つ画面。

#### 2. 販売の流れ（運用フロー）
これが最も現実的で、不正コピーも防げる手順です。

```
① 商品（exe）を渡す
ココナラやBOOTHなどで注文を受けたら、まずは全員共通の tool.exe を送ります（ダウンロードできるようにします）。

② ユーザーから「ID」を受け取る
ユーザーがアプリを開くと、以下の画面が表示されます。

「ライセンス未認証です。
あなたの申請コード: ABC-123 をコピーして、販売者に送ってください。」
ユーザーはメッセージであなたに ABC-123 を送ります。

③ あなたが「キー」を返信してあげる
手元の「キー作成用スクリプト（自分専用）」に、届いた ABC-123 を入力します。
すると、正解の 999-888 が表示されるので、それをユーザーに教えます。

④ 認証完了
ユーザーが 999-888 をアプリに入力します。
アプリ側で「今のPCのID(ABC-123) ＋ 秘密の合言葉」を計算し、入力された 999-888 と一致すれば、**「認証成功！」**としてメイン画面が開きます。
```

#### 3. 次回以降の自動ログインの仕組み
一度認証に成功したら、ユーザーが二度とキーを打たなくて済むようにします。

保存: 認証成功時に、license.json（または設定ファイル）を PCの隠れた場所（AppDataなど） に書き出します。

中身の例: {"id": "ABC-123", "key": "999-888"}

チェック: 次回からアプリを起動する際、まずこのファイルを読み込みます。

「今のPCのID」と「保存されているID」が同じか？

「保存されているキー」が、今のIDから導き出される正解と一致するか？

結果: 両方OKなら、即座にツールが立ち上がります。

#### 4. この方法が「最強」な理由
コピーされても安心:
Aさんが tool.exe と license.json をセットでBさんに渡しても、BさんのPCではHWIDが違うため、アプリが「IDが一致しません」と判断して起動をブロックします。

自給自足できない:
アプリ内に「正解のキー」を計算する式はありますが、**「あなただけが知る秘密の合言葉」**がソースコードに隠されているため、ユーザーは自分のIDから正解を推測することができません。

管理が楽:
exeは1つ作れば使い回せます。あなたは届いたIDを計算して返信するだけです。

💡 実装に向けた最初の一歩
まずは、Go（Wailsの app.go など）で 「自分のPCのHWIDを表示する」 ところから始めてみるのがおすすめです。

Go
// こんな感じのライブラリを使うと1行で取れます
import "github.com/denisbrodbeck/machineid"

id, _ := machineid.ID()
fmt.Println(id) // これが申請コードの元になります

---

- 法人・チーム版: 15,000円（同一拠点内なら何人でもOK）

## アップデート
最新版への誘導（アップデート確認）は、ユーザーの利便性と「古いバグのある版を使い続けられないようにする」という管理の両面で非常に大切ですね。

個人開発で、かつサーバー費用をかけたくない場合の現実的で賢い方法をまとめました。

### 1. どこで確認させるのがいい？（タイミング）
「起動時の確認」がベストです。

理由: アプリを開いた瞬間に「新機能があります！」と出れば、ユーザーは自然に更新してくれます。使っている最中に邪魔されることもありません。

やり方: 起動時にバックグラウンドで「現在のバージョン」と「最新のバージョン」を比較します。

### 2. Webサイトを作る必要はある？
本格的なサイトをイチから作る必要はありませんが、**「最新のバージョン番号が書かれたテキストファイル」**をどこかネット上に置いておく場所は必要です。

おすすめは以下の無料ツールです。

#### A. GitHub（または GitHub Pages）★一番おすすめ
エンジニアならGitHubにソースコード（または公開用リポジトリ）を置くのが一番楽です。

version.txt というファイルに 1.0.1 とだけ書いて置いておきます。

Goのプログラムから、そのファイルのURL（Raw URL）を読みに行くだけで「今、ネット上の最新は何版か」が分かります。

#### B. Google ドライブ（直リンク）
Googleドライブに最新版のexeとバージョン情報のテキストを置き、その直リンクをアプリに覚えさせます。

サイトを管理する手間がなく、ファイルを更新するだけで済みます。

#### C. note や ブログ
「最新版のダウンロードはこちら」という記事を1つ作り、そのURLをアプリ内に「更新ボタン」として貼っておくだけでも十分です。

### 3. 具体的な「誘導」の流れ
アプリ（Wails）側で次のような処理を組むのが一般的です。

- チェック: アプリ起動時に、ネット上の version.txt を読み取る。
- 比較: 自分のバージョン（例: 1.0.0）より新しかったら（例: 1.0.1）、ポップアップを出す。
- 誘導: 「最新版があります。ダウンロードページを開きますか？」とはい/いいえで聞く。
- ジャンプ: 「はい」なら、ブラウザで販売ページ（ココナラ等）や、最新版のダウンロードリンクを開く。

### 4. なぜ「最新版への誘導」が重要なのか
特にライセンス機能を付ける場合、以下のリスクを防ぐために必須となります。

- 古いバグの修正: 姓名分割のロジックを修正したのに、古い版を使っている人から「バグってる」とクレームが来るのを防げます。
- ライセンス破り対策: 万が一、今の認証ロジックが突破された場合、最新版でセキュリティを強化して、古い版を強制的に停止（「このバージョンは利用できません。更新してください」と出す）することができます。

結論
「Webサイト」というよりは、「最新のバージョン番号を置いておく場所」を作ればOKです。

まずは GitHub のパブリックリポジトリか、Googleドライブあたりに「最新版の置き場所」を決めてしまうのが一番簡単ですよ。


## DBの配置
.exe ファイルは、一度ビルドすると中身を書き換えることができないため、データは必ず外付けのファイルとして保存される仕組みになっています。

現状のままだと、配布した時に少し困ったことが起きる可能性があるので、整理してみますね。

### 1. 今のコードで起きる問題
sqlite.Open("app.db") のようにファイル名だけを指定すると、**「カレントディレクトリ（現在アプリを実行している場所）」**にDBファイルが作られます。

- デスクトップで実行した場合: デスクトップに app.db が出現します。
- USBメモリから実行した場合: USBメモリ内に app.db が作られます。
- ユーザーがexeの場所を移動させた場合: 以前の app.db が見つからなくなり、新しい場所でまた「空のDB」が作られてしまいます（＝データが消えたように見える）。

### 2. 理想的な書き換え（AppDataへの保存）
前にお話しした通り、exeをどこに置いてもデータが消えないようにするには、OSが指定する専用の保存場所をフルパスで指定してあげる必要があります。

GORM を使っている場合の書き換え例です：

```go
Go
import (
    "os"
    "path/filepath"
    "log"
    "gorm.io/driver/sqlite"
    "gorm.io/gorm"
)

func InitDB() *gorm.DB {
    // 1. Windowsなら AppData/Roaming、Macなら Application Support のパスを取得
    configDir, err := os.UserConfigDir()
    if err != nil {
        log.Fatal("設定ディレクトリの取得に失敗:", err)
    }

    // 2. 自分のアプリ専用のフォルダパスを作成
    appDir := filepath.Join(configDir, "YourAppName") // "YourAppName"は自由に変更
    
    // 3. フォルダがなければ作成
    if _, err := os.Stat(appDir); os.IsNotExist(err) {
        os.MkdirAll(appDir, 0755)
    }

    // 4. フルパスでDBを開く (例: C:\Users\xxx\AppData\Roaming\YourAppName\app.db)
    dbPath := filepath.Join(appDir, "app.db")
    db, err := gorm.Open(sqlite.Open(dbPath), &gorm.Config{})
    
    if err != nil {
        log.Fatal("データベースの接続に失敗:", err)
    }
    
    return db
}
```
